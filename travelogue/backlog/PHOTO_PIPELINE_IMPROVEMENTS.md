# Photo Pipeline Improvement Backlog

**Status:** OPEN  
**Scope:** MDCR2026 travelogue photo preparation pipeline  
**Validated against:** 2026-08-02 to 2026-08-04 test set

この文書は、旅行記制作で使用する写真処理・Google Drive連携について、現時点で有効な改善提案を記録する。
一時的に発生して解消済みの事象そのものではなく、本番運用で再発を防ぐために実装価値が残っている改善を対象とする。

## 1. Preview画像のファイルサイズ上限を設ける

### 状況

8/2〜8/4の241枚を検証した結果、Preview画像はすべてChatGPTから正常に取得・認識できた。

一方、現在の生成条件（長辺1800px、JPEG quality 82）では、ファイルサイズにばらつきがある。

- 対象: 241枚
- 平均: 約439KB
- 中央値: 約421KB
- 500KB超: 60枚
- 750KB超: 10枚
- 1MB超: 2枚
  - P0110: 約1.11MB
  - P0111: 約1.15MB

### 改善案

Preview生成時に、固定qualityだけでなく目標ファイルサイズを考慮する。

例:

1. 長辺1800pxへ縮小する。
2. quality 82でJPEGを生成する。
3. 目標上限を超えた場合のみqualityを段階的に下げる。
4. 最低qualityを設定し、過度な画質低下を防止する。

初期目標として500〜600KB程度の上限を検討する。

### 完了条件

- 通常のPreviewが目標サイズ付近に収まる。
- 大幅な画質劣化がない。
- ChatGPTによる写真内容・構図・人物・被写体の判定に支障がない。

## 2. Google Driveアップロード完了後の整合性検証を自動化する

### 状況

初回照合時、8/2のmanifestには29枚存在したが、Google Driveのフォルダ一覧では一時的に27枚しか確認できず、以下の2枚が欠落して見えた。

- P0024.jpg
- P0026.jpg

その後、両ファイルは正しい8/2フォルダに反映され、最終的に29/29枚が一致した。

ローカル生成の失敗ではなく、Google Driveへのアップロードまたは反映途中だった可能性が高い。

### 改善案

ChatGPTによる写真処理を開始する前に、日別で以下を照合する。

- manifestに記録されたPreview件数
- Google Drive上のPreview件数
- Previewファイル名の集合

単純な件数一致だけでなく、ID単位で不足・余剰を検出する。

例:

```text
2026-08-02 manifest: 29 / Drive: 29 / OK
2026-08-03 manifest: 149 / Drive: 149 / OK
2026-08-04 manifest: 63 / Drive: 63 / OK
```

不一致時はレイアウト工程へ進まず、欠落IDを表示する。

### 完了条件

- manifestとDrive上のPreviewの全IDを機械的に照合できる。
- 欠落・余剰ファイルがある場合に対象IDを特定できる。
- 全件一致後に写真選定・レイアウト工程へ進める。

## 3. .DS_Store等の不要ファイルをアップロード対象から除外する

### 状況

Google Drive上の `generated/` に `.DS_Store` が含まれていた。

旅行記制作には不要であり、ChatGPTが参照する素材一覧にも混在させる必要はない。

### 改善案

Google Driveへアップロードする際に、少なくとも以下を除外する。

```text
.DS_Store
._*
```

将来的に同期・アップロードスクリプトを作成する場合は、そのスクリプト側の除外条件として実装する。

### 完了条件

Google Drive上の写真作業用ディレクトリに、macOS由来の不要な管理ファイルが存在しない。

---

## 4. 写真IDを本番選定開始後は安定させる

### 状況

現在のPreview生成方式では、原本を撮影日時順に並べた後で `P0001` から連番を割り当てる。

この方式は初期生成には適しているが、後から `originals/` に過去時刻の写真を追加して再生成すると、それ以降のIDが変わる可能性がある。

写真IDは今後、以下から参照される。

- manifest
- Contact Sheet
- 写真選定記録
- 本文との対応
- レイアウト指定

したがって、本番の写真選定開始後にIDが変わると参照関係が壊れる。

### 改善案

8/2〜8/4の試作中は現方式を維持してよい。

全15日分を確定して本番選定へ移る前に、次のいずれかを採用する。

- 全原本を揃えた時点でID採番を固定し、以後再採番しない。
- 元ファイル名または永続キーとIDの対応表を保持し、既存ファイルには以前のIDを再利用する。

後者の方が追加写真への耐性は高い。

### 完了条件

- 一度付与した写真IDが再実行で変化しない。
- 写真追加時は既存IDを維持し、新規写真だけに新しいIDを付与できる。
- manifest、Contact Sheet、写真選定記録の参照が維持される。
